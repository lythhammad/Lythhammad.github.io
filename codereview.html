CS 499 Milestone One: Written Code Review

Introduction

This written code review is being submitted in lieu of a video review as per instructor approval. It covers the same ground as the video review: the existing functionality of each artifact, the areas I felt needed improvement, and the changes I've made in each of the three categories.

The artifact for all three categories is XPLR, a full stack national parks explorer that I built in 2023 at Hack Reactor with four other devs. It's a FastAPI backend with a PostgreSQL database and pulls in data from various external APIs to provide national park information. I went through each component against a checklist for readability, structure, error handling and security.

Category One: Software Design and Engineering

Existing functionality

I examined the back-end API, which consisted of main.py, authenticator.py, and the accounts router. Main.py is what gets run first, that is the beginning of the program. It instantiates the FastAPI application, adds the CORS middleware, and adds the auth, accounts, favorites, parks, and reviews routers as individual modules so that every feature is in a different file instead of on huge file.

Authenticator.py is a wrapper around the third-party jwtdownfastapi library, explaining how the app obtains account data, loads the hashed password, and constructs the cookie payload. The library does the hashing of the password; I am not writing my own cryptography, which is very good. In the accounts router, the create_account endpoint hashes the password, creates the account, and returns a 400 when it encounters a Duplicate Account Error.

Areas identified for improvement

Both allow_origins entries read the same CORS_HOST environment variable with two different fallback values, so when the environment variable is set, they both read the same thing and the expected fallbacks don’t work. Allowed methods and headers are only wildcards, which means it would be insecure for a production application.

In authenticator.py, there is no input validation and no error handling around the account lookup, so a database error would bubble up as an unhandled 500 with no log. In the accounts router, create_account has only one except clause DuplicateAccountError, so any other failure will bubble up as a generic server error. The get_token endpoint also has a code path that 'sends back' None even though its response model is AccountToken, which is not desirable.

Enhancements implemented

In main.py I only parse CORSHOST once in a helper function, I support comma-separated list of origins, I support local origins only when the variable is not set and I've removed the wildcards with a list of the methods and headers that the frontend needs. In authenticator.py I've put a condition to verify that the username is not blank before attempting to query the database, I've wrapped the account lookup in a try/except which logs the full error before re-throwing a generic one, and put in a guard clause in get_hashed_password to handle malformed account objects.

In the accounts router, I introduced validation of username and password for creating an account, the more general exception handling of create_account, the subsequent auto-login of create_account and account listing and I changed get_token so every path produces a return value that conforms to the response model.

Category Two: Algorithms and Data Structures

Existing functionality

I looked into the reviews query module. It is used to insert, get, and delete park reviews in the shared ConnectionPool against the PostgreSQL database. Get_user_reviews and get_all_reviews pull back raw rows, then iterate over each row and construct a dictionary with the column names in cur.description as keys, and the row values as values.

Areas identified for improvement

The same row-to-dictionary loop used in create_review and get_user_reviews is copied in the get_all_reviews methods. This is some copy-pasted logic that should be in a single helper method. get_all_reviews can't sort or filter, so the reviews just come back in the order the database spits them out. Most crucial for this category, the module stores the data but does nothing with it, like determining the average rating for a park.

Enhancements implemented

I extracted the duplicated conversion into a static function, rowtodict, that was called by each of the functions that interacts with the reviews table. I enhanced get_all_reviews by adding parkcode and sortby parameters so reviews can be filtered by park and sorted by rating (highest first) or by newest first. I also added get_average_ratingby_park, which uses SQL aggregate functions, AVG and COUNT, so the database returns only one value instead of the app downloading all the reviews and doing the math itself. I decided to do the average calculation on demand rather than cache it, an appropriate tradeoff given the current dataset.

Category Three: Databases

Existing functionality

I examined pool.py and the favorites and reviews query modules. Pool.py instantiates one ConnectionPool from psycopg_pool using the connection string set in the DATABASE_URL environment variable. The query modules use the pool as a context manager to obtain a connection and cursor for each request. The pool lets the app reuse connections, and each connection goes back to the pool when the request ends, even if an error happens partway through. The queries I looked at use parameterized %s placeholders instead of string formatting, which protects against SQL injection.

Areas identified for improvement

Nor did any of the database methods have error handling, which meant that a failure to complete the query, a dropped connection, or an exhausted pool would show up as an ugly unhandled exception. Nothing in the favorites table stopped the same user from favoriting the same park more than once. Get_all_favorites and get_all_reviews retrieved every row in their tables with no limit; this doesn't work well when the tables become large.

Enhancements implemented

In pool.py I added in error handling to log a nice message that DATABASEURL is not set or could not build a pool and a getconnection helper that logs errors when connecting to the database (and pool timeouts). In favorites.py and reviews.py I wrapped every database call in a try/except statement that logs the entire exception before raising it again. I wrote a migration that sets a unique constraint on user_id and parkcode in favorites table, and create_favorite now catches the UniqueViolation that results and raises a clear DuplicateFavoriteError. I also added limit and offset parameters, defaulting to fifty rows, to the get_all_favorites and get_all_reviews functions.

Alignment with the Course Outcomes

Collaborative environments

I've done code reviews for SNHU, Study.com, and Hack Reactor. This review is the same checklist a team would go through and is organized so a peer or manager can see what the code does, what is weak, and what changed. XPLR itself was built by 5 people.

Professional communication

The review defines what each artifact does, the problems present, and the rationale for each change for a peer/manager audience in plain language.

Algorithmic solutions and trade-offs

The reviews module rewrite removes duplicate logic, adds filtering and sorting, and moves the average calculation into SQL. This was a trade-off by doing the average on demand rather than caching it.

Well-founded techniques

A database-level unique constraint, pagination, centralized helper functions, and consistent error handling and logging are best practices to improve the quality of your code.

Security mindset

Limiting CORS, filtering the input, confining errors without leaking internal information, and enforcing data integrity all come from examining the code the way an attacker or a malfunctioning system would.

Closing

But we identified the following regular areas where we could improve: error handling, input validation, database-level integrity, and (for the algorithms) actual processing of stored data.
